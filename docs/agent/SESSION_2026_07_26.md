## Phase 0: Fix `zad_users.budget` Corruption

### Problem
Server trigger `update_budget_on_transaction` was treating `zad_users.budget` as "remaining balance" instead of "ceiling":
- Client set it via `updateUserBudget()` (monthly ceiling edit in BudgetScreen)
- Trigger decremented it on every transaction insert
- `ZadViewModel.loadBudget()` pulled this corrupted value, overwriting correct local cache almost every app open

### Solution
**Migration (inline in code):** Drop corrupting trigger + function.

**`ZadViewModel.loadBudget()` logic flip:**
```kotlin
// OLD: unconditionally pull server value over local cache (wrong)
// NEW: if local cache exists, push it to server (local is source of truth)
if (prefs.contains("cached_budget")) {
    SupabaseRepo.updateUserBudget(cachedBudget)  // push local → server
} else {
    val serverBudget = getUserBudget()  // only pull on first ever load
    prefs.edit().putFloat("cached_budget", serverBudget.toFloat()).apply()
}
```

**Trade-off:** Budget edit on device A won't reach device B until B's cache cleared. Acceptable vs corruption.

## Phase 1: Unify BankTransactionApplier

### Problem
Three SMS receiver paths + two notification paths all duplicated insert+sync+budget logic inline (copy-paste risk).

### Solution
Replace all paths with `BankTransactionApplier.apply(context, transaction)`:
- `UnifiedSmsReceiver` (primary parse, regex fallback, AI fallback)
- `UnifiedBankListener` (primary parse, already had AI fallback)
- Keep `TxDeduplicator` check + `REFUND` branching (applier optional param)
- Add `SyncOutbox.enqueueUnparsedNotification()` retry when amount extractable but parse failed

**Result:** Single path for insert/Supabase-sync/budget, consistent across all sources.

## Phase 2: Family Scoping & Server Dedup

### Problem
1. No family-level view of member transactions (parent can't see child's spending)
2. Shared joint-card SMS lands on both phones, both insert duplicate rows (local `TxDeduplicator` only sees own device)

### Solution

**New migration (applied to live):**

1. **Column:** `ALTER TABLE zad_transactions ADD COLUMN family_id UUID`
2. **Trigger:** `populate_and_dedupe_family_transaction()` BEFORE INSERT
   - Server-derives `family_id` from `family_members WHERE user_id = NEW.user_id`
   - Prevents duplicate if same amount/is_expense from different admin in same family within 5 min
   - Scoped to `role='admin'` only — children's transactions never deduped this way

3. **RLS policy:** `family_admin_read_child_transactions`
   - Additive SELECT policy (doesn't affect insert/update/delete)
   - Admin can read child's zad_transactions rows if both in same family

4. **Indexes:** `(family_id, created_at)`, `(family_id, user_id)` for dashboard queries

## Phase 3: Scope BudgetTracker/TxDeduplicator by user_id

### Problem
SharedPreferences keys had no user suffix:
- Multiple family members on shared tablet → budgets/dedup fingerprints leak into each other
- Direct `SupabaseRepo.client.auth.currentUserOrNull()` call from these storage utilities crashed Robolectric tests (Auth init needs real Context)

### Solution

**New `CurrentUser.kt` cache:**
```kotlin
object CurrentUser {
    fun cache(context: Context, userId: String?) { /* SharedPreferences */ }
    fun get(context: Context): String? { /* SharedPreferences */ }
}
```
- No SupabaseRepo dependency
- Written after MainActivity's `awaitInitialization()` + AuthViewModel's sign-in success
- Read-only from BudgetTracker/TxDeduplicator

**BudgetTracker changes:**
- All keys now suffixed: `scopedKey(context, "budget")` → `"budget_userid"`
- Legacy fallback: `readLegacyFloat()` preserves existing users' balances

**TxDeduplicator changes:**
- Prefs name now user-scoped: `"zad_tx_dedup"` → `"zad_tx_dedup_userid"`
- No legacy fallback (10-min fingerprint window, safe to start fresh per user)

**Result:** All 69 unit tests pass (Robolectric no longer crashes on auth init).

## Phase 5: Server-Side Parent Alerts

### Problem
Parent can see child's real spending now, but gets no notification when thresholds crossed (only if they happen to check app).

### Solution

**New migration (applied to live):** `20260726100000_parent_alerts_child_spending.sql`

**New table:**
```sql
CREATE TABLE sent_budget_alerts (
    id UUID PRIMARY KEY,
    user_id UUID,
    threshold INT,        -- 75, 90, 100
    month TEXT,           -- YYYY-MM
    created_at TIMESTAMP,
    UNIQUE(user_id, threshold, month)  -- idempotency
);
```

**AFTER INSERT trigger:** `notify_parents_on_child_spend()`
1. Only fires when `is_expense=true` and `user_id.role='child'`
2. Sum all child's expenses this month
3. Check vs child's `zad_users.budget` ceiling → compute %
4. Determine highest new threshold (100→90→75) not already sent this month
5. If new threshold: insert one `app_notifications` row per family admin
6. Messages in Arabic: "⛔ ميزانية X امتلأت" / "⚠️ ميزانية X قاربت النفاد" / "💡 ميزانية X 75%"

**Result:** Parents get server-side push when child crosses threshold, even if offline.

## Key Design Decisions

### 1. Local-first budget truth (Phase 0)
**Decision:** `cached_budget` in SharedPreferences is source of truth; Supabase is a cache.  
**Why:** Corruption bug showed server can't be trusted. Client owns the edit. Push-on-load is safer than pull-on-load.  
**Trade-off:** Multi-device sync requires manual cache clear.

### 2. CurrentUser cache instead of SupabaseRepo (Phase 3)
**Decision:** BudgetTracker/TxDeduplicator read CurrentUser (SharedPreferences-only), not SupabaseRepo.client.  
**Why:** Storage utilities shouldn't own network client dependency. Avoids Auth init on every test. Simpler dependency graph.  
**Trade-off:** CurrentUser must be manually synced in MainActivity + AuthViewModel.

### 3. Server-only v1 dedup (Phase 2)
**Decision:** Trigger prevents duplicate row server-side, but each phone's local BudgetTracker may still deduct twice.  
**Why:** Server-side correctness is critical (family aggregates are correct). Local double-deduction on shared device is acceptable for v1 (documented, can be fixed later with cross-device sync).  
**Trade-off:** Not a complete solution, but shipping fast without new infrastructure.

### 4. Same thresholds for all (Phase 5)
**Decision:** Children use same 75/90/100% thresholds as adults.  
**Why:** Simpler UX. Parents set child's individual `zad_users.budget` ceiling, same alerts fire.  
**Why not daily_limit/weekly_limit:** Those columns belong to chore/allowance system (separate data flow). Real spend thresholds track actual bank activity, different concern.

### 5. Realtime subscription admin-only (Phase 4)
**Decision:** `startRealtimeFamilySpending()` only called when `myMemberInfo.role == 'admin'`.  
**Why:** Children don't need live spending notifications (parents do). RLS already enforces read access.  
**Trade-off:** Non-admin in same family can see spending on load, but won't get live updates. Fine — UX expectation is admin-centric dashboard.

## Architecture Notes

### Budget Flow (Post-Phase-0)
```
Device A (local)                 Supabase
  SharedPreferences                 zad_users.budget
  "cached_budget" ──push──────→     (ceiling only, never "remaining")
                 ◄──pull once───     (on first load only)
```

### Transaction Flow (Post-Phase-2)
```
SMS/Notification ─→ UnifiedBankListener ─→ BankTransactionApplier
                    UnifiedSmsReceiver   ┕→ TxDeduplicator (device-local, 10min window)
                                        ┕→ Room insert
                                        ┕→ SupabaseRepo.addTransaction()
                                             ┕→ Server: populate_and_dedupe_family_transaction()
                                                 (family_id + 5min joint-card dedup)
```

### Family Dashboard Flow (Post-Phase-4)
```
Parent opens FamilyScreen
  ├─ loadFamilyData() ─→ getMyFamilyMember()
  ├─ fetchFamilyDetails() ─→ fetch members + messages + goals + chores
  └─ startRealtimeFamilySpending() ─→ RealtimeChatRepo.subscribeToChat()
     ┕→ RealtimeFamilySpendingRepo.subscribeToFamilyTransactions()
        ┕→ On new INSERT: loadChildrenSpending()
           ├─ getFamilyMemberTransactions(familyId)  [RLS-filtered]
           ├─ getUsersBudgets([child1_id, child2_id, ...])
           ├─ Aggregate per-child: sum(amount by category, by month)
           └─ Update _childrenSpending StateFlow
              ┕→ KidsSpendingTab renders: SpendLimitBar for each child
```

### Alert Flow (Post-Phase-5)
```
Child adds transaction (any source)
  ┕→ INSERT into zad_transactions
     ┕→ Server trigger: notify_parents_on_child_spend()
        ├─ Check: is_expense? user.role='child'?
        ├─ Compute: month_spent vs budget → pct
        ├─ Determine: highest new threshold (100→90→75)
        ├─ Log: sent_budget_alerts (idempotency)
        └─ Insert per admin: app_notifications row
           ┕→ NotificationCenterScreen displays + push if device online
```

## Key Learnings

1. **Direct network client calls from storage utilities = bad.** CurrentUser cache pattern is cleaner.
2. **Idempotency guards at schema level (unique index) > application-level dedup.** Cheaper, more reliable.
3. **RLS policies OR multiple permissive policies, don't replace.** Parent + child read access both needed, handled with two separate SELECT policies.
4. **Server trigger timing matters.** BEFORE vs AFTER determines what data is available inside the trigger function. BEFORE for populating derived columns, AFTER for notifications.
